# Taste
- Clarifies terse UI requests with terse follow-ups and expects literal interpretation of the named target: when they said clicking "WorkingRow" should "highlight first row", they meant the WIP row itself should get the highlighted/selected state (like commit rows), not that the click should select/highlight a different row (e.g. the HEAD commit) — "first i mean WIP row it self". Reads requests literally rather than reinterpreting the target. Confidence: 0.6
- Prefers a plan/architecture-first workflow: when starting a new project, wants the assistant to propose architecture and a phased plan before writing code ("plan and sugest me the architecture"). Confidence: 0.85
- Values verifying against real-world data: when parsers/interfaces target external tools (e.g. git), checks the actual command output against a real repository before trusting fixtures. Confidence: 0.7
- Chose Tauri 2 + React + TypeScript (Rust backend) for a desktop GUI over Electron, and prefers shelling out to the real `git` CLI over git libraries (libgit2/isomorphic-git). Confidence: 0.7
- Prefers custom, dependency-light implementations for core rendering logic (hand-rolled canvas graph + virtualized rows + pure, unit-tested layout algorithm) over pulling in a graph library. Confidence: 0.7
- Prefers native, platform-standard dialogs (official Tauri plugin-dialog with a directory picker) over web-view hacks (e.g. `webkitdirectory` file inputs) for file/folder selection — a "Browse" button must open a native folder picker, not a file chooser. Confidence: 0.6
- Chose full-feature scope (merge/rebase/cherry-pick/stash UI) over a minimal v1 when building a git client — prefers complete workflows over MVP cut-downs. Confidence: 0.6
- Dislikes silent failures: reports bugs like "nothing happen" after an action and expects UI actions to either work or surface a visible error (e.g. alert) rather than failing silently (reported "modified file not showing any changes in diff-viewer" when the diff silently returned empty hunks for untracked files; reported "click on WIP row not happen anything (CommitComposer not showing)" when a refactor dropped the composer-open behavior). Confidence: 0.8
- Iterative hands-on tester: user runs the app themselves after each fix and reports back remaining issues in terse, symptom-focused batches ("graph drawing still wrong", "selecting commit not showing the detail on sidepanel", "only new file colored, modified and deleted still has no color"), often attaching a screenshot to illustrate the GUI symptom, and expects the assistant to address all listed issues in the next round rather than stopping at the first fix. Confidence: 0.7
- Prefers smooth, rounded curves over sharp right angles in rendered visualizations (asked graph connector lines to curve instead of a "90deg L shape"); favors polished, natural-looking geometry (e.g. rounded corners proportional to lane width) once the core logic works. Confidence: 0.6
- Prefers UI consistency: when a new surface duplicates a pattern that already exists in the app, wants it to reuse that same component/look rather than a new ad-hoc layout — e.g. asked the composer's Unstaged/Staged lists to "look like file tree, similar to CommitDetail's file tree", prompting the tree builder + FileTree to be generalized into shared/. Confidence: 0.8
- Prefers compact forms with minimal chrome: field placeholders act as the titles/labels (no separate visible `<label>`), inputs sized compactly, and message fields placed adjacent to the primary action (Subject/Description at the bottom, just above the Commit button). Confidence: 0.7
- Prefers UI panels/lists to fill the available space rather than sit at content height leaving dead space — explicitly asked both staging file trees to "stretch (flex-grow)" to fill the pane. Confidence: 0.6
- Directs UI changes in terse, implementation-level terms using technical vocabulary (e.g. CSS property names like "flex-grow", class selectors like ".diff-col stretch to bottom") and expects them applied directly rather than re-interpreted; often pins the exact file/component (e.g. "click on WorkingRow, should highlight first row") and lets the assistant decide the mechanics. Confidence: 0.7
- Does not want the assistant to auto-commit work — commits should happen only when the user explicitly asks ("dont immediately commit this project unless i ask you to commit"). Confidence: 0.9
- Wants core project documentation before going further on a project: asked for a README.md (what it is, features, prerequisites, setup, scripts, architecture) and a ROADMAP.md (phase-based tracker of done/in-progress/planned work) to be in place early and reflect the current state; continues to actively use the ROADMAP as the living tracker for planned features (e.g. asked to add an AI integration phase covering generate commit message, compose/group commits by change context, and generate PR). Confidence: 0.8
- When choosing a project name, values names that don't collide with existing products/trademarks — rejected "GitLens" (Axosoft's product) and "GitTree" (already taken) before settling on "GitCanoe". Confidence: 0.4
 Prefers full-file context in diff views: wants the entire old and new file rendered side-by-side with changed regions highlighted, not just the changed hunks — with guards so very large files or high change density fall back to a compact hunk-only view or a "file too large" notice. Confidence: 0.6
- For side-by-side diffs, both panes (old vs new) must always be visibly present: added files show an empty/placeholder old side with all content as additions on the new side, deleted files show content on the old side with an empty/placeholder new side — never mirror content onto both sides or let one column appear blank/collapsed, since a side-by-side viewer is expected to "show 2 contents, old vs new" ("diff viewer side-by-side should be showing 2 contents, old vs new. currently if open added file. if show only new content. on deleted file too"). Followed up ("still not working, i think it caused by HunkView fallback") when an alternate render path still produced a single column — the requirement must hold on every render path, not just the main one. Confidence: 0.9
- Prefers wide layouts for diff viewing: a side-by-side diff should replace the full left panel (the commit graph) to maximize horizontal space rather than squeeze into the narrower right pane. Confidence: 0.5
- Prefers compact close controls in full-pane views: an "X" button at the top-right to close, over a labeled "← Back" button. Confidence: 0.4
- Prefers small utility functions collected into a dedicated folder rather than scattered inline in components ("refactor all small utils function into folder src/utils, more organizer"). Confidence: 0.6
- Keeps an eye on file size and proactively asks to refactor files that "start became fat" — flagged the single global CSS file and accepted splitting it by feature area (base/repo/workspace/commit-list/detail/file-tree/composer/diff, matching the feature folders) with the original file kept as an entry that `@import`s the parts, so each area's styles land in a dedicated file. Confidence: 0.6
- Wants every git state handled correctly, including edge cases: unstaged/untracked (new) files, staged-only changes (index vs HEAD), and root commits — expects the diff tool to synthesize/show changes for untracked files rather than showing nothing because `git diff` ignores them. Untracked (`??`) files must also get a proper colored status in UI lists (rendered as green "added"/plus like other new files) rather than a colorless/gray unknown state. Confidence: 0.7
- Wants errors surfaced in the UI instead of swallowed: when a command fails, the diff view should display the actual error message rather than a permanent "Loading…" or an empty result. Confidence: 0.7
- Prefers full content over truncation in code/diff views: long lines should expand the row and trigger horizontal scroll (max-content columns, `white-space: pre`) rather than being clamped to the container and ellipsized ("need horizontal scroll for DiffView"). Confidence: 0.5
- Prefers the side-by-side diff to behave like two synchronized text editor panes, not one monolithic scrollable table: a single shared vertical scroll keeps both panes in sync, and the two columns' horizontal scroll must ALSO be synced — scrolling one side mirrors the other ("make both .diff-col sync scroll") — with exactly one horizontal scrollbar per side at the column bottom. Explicitly rejected the previous single-table horizontal scroll ("currently scroll is along .diff-table side... it should look like 2 text editor that sync scrolled") and rejected per-row scrollbars ("now it worse, scroll shown every row"). Line-number gutters pinned (sticky) while line content scrolls. Confidence: 0.9
- Wants project conventions (folder structure, import rules) codified in AGENTS.md project memory so agents follow them consistently; asked "how ensure Agent keep the rules?" and approved drafting AGENTS.md as the mechanism. Confidence: 0.6
- Prefers mutually-exclusive controls collapsed into a single toggle that flips label/state rather than showing both buttons at once (asked to make "Expand all"/"Collapse all" a single toggled button). Confidence: 0.5
- Prefers compact status summaries: hide UI rows when there is nothing to show, and use per-type icon + count badges (e.g. "WIP" with modified/added/deleted counts) over verbose wording ("hide if Working Dir clean, update wording to WIP with [icon] [number of files]"). Confidence: 0.5
- Wants syntax highlighting for known file types in code/diff views, with a plain-text fallback for unknown extensions ("i think i need syntax highlighter for known extentions"). Confidence: 0.5
- Wants scrollbars/controls always visible and reachable without scrolling first: flagged the diff's horizontal scrollbar only appearing after scrolling to the bottom as "not very UX friendly" and accepted an always-visible scrollbar strip pinned at the bottom of the view (detached from the content, driving both columns' horizontal scroll). Confidence: 0.7

Confidence: 0.9
