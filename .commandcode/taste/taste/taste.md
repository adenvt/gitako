# Taste
- Prefers a plan/architecture-first workflow: when starting a new project, wants the assistant to propose architecture and a phased plan before writing code ("plan and sugest me the architecture"). Confidence: 0.8
- Values verifying against real-world data: when parsers/interfaces target external tools (e.g. git), checks the actual command output against a real repository before trusting fixtures. Confidence: 0.7
- Chose Tauri 2 + React + TypeScript (Rust backend) for a desktop GUI over Electron, and prefers shelling out to the real `git` CLI over git libraries (libgit2/isomorphic-git). Confidence: 0.7
- Prefers custom, dependency-light implementations for core rendering logic (hand-rolled canvas graph + virtualized rows + pure, unit-tested layout algorithm) over pulling in a graph library. Confidence: 0.7
- Prefers native, platform-standard dialogs (official Tauri plugin-dialog with a directory picker) over web-view hacks (e.g. `webkitdirectory` file inputs) for file/folder selection — a "Browse" button must open a native folder picker, not a file chooser. Confidence: 0.6
- Chose full-feature scope (merge/rebase/cherry-pick/stash UI) over a minimal v1 when building a git client — prefers complete workflows over MVP cut-downs. Confidence: 0.6
- Dislikes silent failures: reports bugs like "nothing happen" after an action and expects UI actions to either work or surface a visible error (e.g. alert) rather than failing silently. Confidence: 0.6
- Iterative hands-on tester: user runs the app themselves after each fix and reports back remaining issues in terse, symptom-focused batches ("graph drawing still wrong", "selecting commit not showing the detail on sidepanel"), often attaching a screenshot to illustrate the GUI symptom, and expects the assistant to address all listed issues in the next round rather than stopping at the first fix. Confidence: 0.6
- Prefers smooth, rounded curves over sharp right angles in rendered visualizations (asked graph connector lines to curve instead of a "90deg L shape"); favors polished, natural-looking geometry (e.g. rounded corners proportional to lane width) once the core logic works. Confidence: 0.6
- Prefers UI consistency: when a new surface duplicates a pattern that already exists in the app, wants it to reuse that same component/look rather than a new ad-hoc layout — e.g. asked the composer's Unstaged/Staged lists to "look like file tree, similar to CommitDetail's file tree", prompting the tree builder + FileTree to be generalized into shared/. Confidence: 0.8
- Prefers compact forms with minimal chrome: field placeholders act as the titles/labels (no separate visible `<label>`), inputs sized compactly, and message fields placed adjacent to the primary action (Subject/Description at the bottom, just above the Commit button). Confidence: 0.7
- Prefers UI panels/lists to fill the available space rather than sit at content height leaving dead space — explicitly asked both staging file trees to "stretch (flex-grow)" to fill the pane. Confidence: 0.6
- Directs UI changes in terse, implementation-level terms using technical vocabulary (e.g. CSS property names like "flex-grow") and expects them applied directly rather than re-interpreted. Confidence: 0.5
- Does not want the assistant to auto-commit work — commits should happen only when the user explicitly asks ("dont immediately commit this project unless i ask you to commit"). Confidence: 0.9
